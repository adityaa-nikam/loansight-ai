# PART 2 — The full technical narrative

## 2.1 The domain problem

Retail loan origination has five stages: **apply → collect documents → verify → underwrite → sanction.**
LoanLens attacks **verify** — the only stage that is still fully manual, and the stage where identity and income fraud actually enters the funnel.

A typical salaried home-loan file contains **6+ documents**: PAN card, Aadhaar card, salary slip, 6-month bank statement, Form 16, property papers. An officer must read all of them and answer one question: *do these documents describe the same person, earning the money they claim?*

Today that question is answered by a human, from memory, under time pressure, with no tooling.

## 2.2 The four sub-problems (M1 numbers these on slide 2; every later slide tags back to them)

**P1 — Documents are verified in isolation, never against each other.**
Existing tooling validates *one* document (is this PAN well-formed? does this Aadhaar exist?). Nothing compares the *name on the salary slip* to the *name on the PAN*. A file where every individual document is valid can still be internally contradictory — and that contradiction is exactly what fraud looks like.

**P2 — The officer gets files, not explanations.**
Even where a system flags a file, it returns a score. An officer cannot act on "risk: 62". They need: *which two documents disagree, on what field, by how much.*

**P3 — The applicant is left in the dark.**
Applicants receive "documents required" or a rejection with no reason. They re-upload blindly, the cycle repeats, and drop-off follows.

**P4 — No auditable trail behind a decision.**
Lending is regulated. A verdict must be reproducible months later — which rule fired, on what evidence, at what time.

## 2.3 The research gap

**The existing landscape, and why each category fails:**

| Category | Examples | What it does | Why it doesn't solve P1–P4 |
|---|---|---|---|
| OCR / IDP platforms | Google Document AI, AWS Textract, Azure Form Recognizer, Mistral OCR | Convert documents into structured text/fields with high accuracy | Extraction only. Zero cross-document reasoning. They tell you *what* the document says, never whether it *agrees* with the next one. |
| KYC / identity verification APIs | Aadhaar & PAN verification services, digital KYC vendors | Validate one document against one authoritative registry | Single-document, single-registry. Blind to a valid PAN sitting next to a salary slip in a different name. |
| LOS / loan-origination suites | Bank core LOS platforms, Finastra-class systems | Workflow, forms, task routing, status tracking | Verification remains a human checklist item inside the workflow. The software moves the file; it doesn't read it. |
| Credit risk / scoring models | Bureau scores, ML default-prediction models | Predict default probability from structured features | **Assume their inputs are already true.** They score an income figure; they never test whether that figure is supported by the documents. Garbage-in is invisible to them. |

**The gap, in one sentence — this is your thesis statement:**

> *Every existing tool either validates a document in isolation or scores an applicant from data assumed to be correct. None of them verify that an applicant's own documents are consistent with each other, and none of them explain that verdict to the officer who must sign off or the applicant who must fix it.*

**Secondary gap — explainability.** A wave of "AI loan approval" projects hand the decision to an LLM. That is unusable in regulated lending: non-deterministic, unauditable, and prone to inventing figures. The gap is not "add AI to lending" — it is **auditable AI in lending**.

## 2.4 Our architectural thesis: rules decide, the LLM explains

This is the single most important intellectual point in the presentation. Say it in exactly these terms:

| | Pure rules engine | Pure LLM | **LoanLens hybrid** |
|---|---|---|---|
| Reads messy scans | ✗ | ✓ | ✓ (LLM extracts) |
| Deterministic verdict | ✓ | ✗ | ✓ (Python decides) |
| Reproducible for audit | ✓ | ✗ | ✓ |
| Human-readable explanation | ✗ | ✓ | ✓ (LLM narrates) |
| Can invent a number | ✗ | ✓ | ✗ (guardrailed) |

**Implementation of the boundary:** all arithmetic and all comparisons happen in `deterministic_validator.py` — plain Python, no LLM. The LLM receives the *finished* check results and writes prose. It is structurally incapable of changing a verdict.

Our code even enforces this numerically: if the LLM's `verificationScore` deviates by more than **25 points** from the Python-computed score, **the Python score wins** (`groq_reasoning.py:341`). Quote this line in Q&A — it is proof, not a promise.

**Why three services, not one** (a real interview-grade answer):
1. **Language fit** — the ML/OCR ecosystem is Python; the transactional web app is JavaScript. Neither language is forced out of its strength.
2. **Security boundary** — the AI service has **no auth layer and no browser exposure**. CORS allows only `localhost:5000` and `localhost:5173`. All authorization is decided in Node before the AI service is ever reached.
3. **Independent scaling** — document processing is slow and bursty; the API is fast and steady. They scale on different curves.
4. **Failure isolation** — the AI service can be down and the portal still works; verification is simply marked pending.

## 2.6 Layer 1 — Document Intelligence

**Input reality:** phone photographs, flatbed scans, native PDFs, employer-specific salary-slip layouts, bank-specific statement formats. Constraints enforced in code: **max 10 MB**, extensions `.pdf .jpg .jpeg .png`, bank statements capped at **10 pages**.

**The pipeline:**

```
upload → hash (dedupe) → text layer extraction → [OCR fallback]
       → classification → schema-bound structured extraction → validated fields
```

**Step 1 — Text extraction with graceful degradation** (`mistral_extractor.py`)
Try the PDF's **native text layer** via PyMuPDF first — it is free, instant and lossless. If the document is a scan with no text layer, fall back to **OCR** with image preprocessing (`_preprocess_for_ocr`). The result is tagged `extraction_method: 'native' | 'ocr'` so downstream code knows the provenance of every field.

**Step 2 — Classification** (`classification.py`)
Gemini `gemini-3.5-flash` classifies the document type. **Two paths:** if usable text exists, classify from text (cheap); if the text is empty or garbage, classify from the **image via vision** (`_classify_from_vision`). Returns a type plus confidence.

**Step 3 — Schema-bound extraction** (`mistral_extractor.py` + `schemas/`)
Mistral `mistral-small-2506` extracts fields using **LangChain `with_structured_output(schema_cls)`** against a Pydantic schema per document type — `identity.py`, `salary_slip.py`, `bank_statement.py`, `form16_itr.py`, `payment_slip.py`. This is the critical design choice: **the LLM cannot return free text, only a validated typed object.** A malformed response fails schema validation and is retried, rather than silently poisoning the verification stage.

**Step 4 — Production hardening** (`config.py`)
Gemini is rate-limited in code for free-tier safety: **10 RPM, max 3 retries on 429/503, concurrency 1**. Prompts are versioned (`prompt_version: v2`) so caches can be invalidated deliberately.

**Failure philosophy:** unreadable input produces *"could not be verified"* — never a silent pass. Downstream checks only run when the fields they need actually exist.

## 2.7 Layer 2 — The Verification Engine (the 9 checks, with real thresholds)

`deterministic_validator.py`, 600 lines, **zero LLM calls**. Comparison primitives: `fuzzy_similarity` (Python `difflib.SequenceMatcher`, with a 0.9 shortcut for substring containment), `normalize_text`, `parse_numeric`, `normalize_pan_str` (regex `[A-Z]{5}[0-9]{4}[A-Z]`), `normalize_date_str`.

### Identity checks

**1. `IDENTITY_NAME_MATCH`** — collects the name from every available source (Declared, PAN, Aadhaar, Salary Slip, Bank Statement, Form 16), computes pairwise fuzzy similarity against the declared name, and keeps the **lowest** score.
| Lowest similarity | Verdict |
|---|---|
| ≥ 0.85 | PASSED / LOW |
| 0.70 – 0.85 | WARNING / MEDIUM ("initials or abbreviations") |
| < 0.70 | **FLAGGED / HIGH**, with every mismatching pair named |

*Our live case: 0.17 → FLAGGED / HIGH.*

**2. `DOB_CONSISTENCY`** — PAN DOB vs Aadhaar DOB, digit-normalised. Equal or substring → PASSED; otherwise **FLAGGED / HIGH**.

**3. `PAN_CONSISTENCY`** — PAN from PAN card, salary slip and Form 16, regex-normalised. All identical → PASSED; any divergence → **FLAGGED / HIGH**.

**4. `AADHAAR_VERIFICATION`** — 12-digit format validation. Valid → PASSED / LOW; otherwise **WARNING / MEDIUM** ("could not be fully verified").

### Employment check

**5. `EMPLOYER_CONSISTENCY`** — salary slip employer vs Form 16 employer, fuzzy.
≥ 0.75 PASSED · 0.50–0.75 WARNING / MEDIUM (legal-name variation, e.g. "Infosys" vs "Infosys Ltd.") · < 0.50 **FLAGGED / HIGH**

### Income checks

**6. `DECLARED_VS_SLIP_INCOME`** — `|declared − slip_net| / declared × 100`
≤ 20% PASSED · ≤ 35% WARNING / MEDIUM · **> 35% FLAGGED / HIGH**
*Live cases: 153.8%, 426.5%, 5171.7%.*

**7. `SLIP_VS_BANK_SALARY`** — averages the **salary credit entries** found in the bank statement and compares to slip net pay.
≤ 20% PASSED · ≤ 35% WARNING · > 35% FLAGGED / HIGH
**Zero salary credits found → WARNING / MEDIUM** — "no recurring salary credit entries identified". This is the check that catches a fabricated employer.

**8. `SLIP_VS_FORM16_INCOME`** — annualises the slip (`monthly × 12`) and compares to Form 16 gross.
≤ 25% PASSED · ≤ 40% WARNING · > 40% FLAGGED / HIGH (wider band than check 6 because bonuses and variable pay legitimately widen annual figures)

### Obligation check

**9. `EXISTING_EMI_BURDEN`** — sums EMI debits detected in the bank statement, computes `DTI = total_EMI / monthly_income × 100`.
**DTI > 50% → WARNING / HIGH** · otherwise PASSED / LOW

### Aggregation (`deterministic_validator.py:583`)

```
any FLAGGED  or  any HIGH-severity WARNING → REVIEW_REQUIRED / HIGH
any MEDIUM WARNING                         → REVIEW_REQUIRED / MEDIUM
fewer than 2 checks could run              → INCOMPLETE / MEDIUM
otherwise                                  → CONSISTENT / LOW
```

### Verification score (`groq_reasoning.py:82`) — every point is traceable

```
base    = 40 + (passed / total) × 60
penalty = (flagged × 8) + (warnings × 3)
score   = clamp(base − penalty, 10, 100)

caps:  REVIEW_REQUIRED and score > 75  →  72
       HIGH severity   and score > 65  →  min(score, 55)
```

**Every check also carries `evidence`, `sourceA` and `sourceB`** — the two sides of the comparison, pre-formatted for side-by-side display. That is what makes the UI explainable rather than decorative.

## 2.8 The reasoning layer and its guardrails

`groq_reasoning.py` sends the **finished** check list to Groq `llama-3.3-70b-versatile` at `temperature=0.1` with `with_structured_output(GroqReasoningOutput)`. It returns `summary`, `keyFindings` (3–5 bullets), `findings[]` (title, subtitle, severity, explanation, sourceA/sourceB), `riskLevel`, `verificationScore`, `recommendedAction ∈ {APPROVE_RECOMMENDED, MANUAL_REVIEW, REQUEST_ADDITIONAL_DOCS}`.

**Four guardrails, all in code — quote these verbatim on slide 8:**

1. **Compliance language enforced.** The system prompt forbids the words *"fraudulent", "fake", "forged"*. Permitted vocabulary: *"discrepancy detected", "verification required", "income variance"*. We are not in the business of accusing customers.
2. **No decision authority.** *"Do NOT make definitive loan approval/rejection decrees. The final credit decision strictly remains with the human loan officer."*
3. **No invention.** *"Do NOT invent information not present in the checks or evidence."*
4. **Numeric override.** If the LLM's score drifts more than 25 points from the deterministic score, the deterministic score replaces it.

**Resilience:** if `GROQ_API_KEY` is absent or the API fails, `_generate_fallback_reasoning()` produces a complete rule-based narrative from the same checks — mapped titles, subtitles, document sets and evidence bullets for all 9 check types. **The product never shows a blank verification screen.** This is a genuine engineering strength; say it out loud.

## 2.9 The Hybrid RAG Loan Assistant

`policy_rag.py` (233 lines) + `loan_officer_assistant.py` (548 lines).

**Corpus:** **14 policy chunks** across **7 categories** — `personal` (3), `home` (3), `lap` (2), `business` (2), `education` (2), `underwriting` (1), `kyc_underwriting` (1). Each chunk carries rules, numeric thresholds, key required documents, `sourceDocument` and `citationUrl`.

**Retrieval is genuinely hybrid — explain both halves:**
- **Dense:** ChromaDB collection `bank_policies`, queried for a ranking boost of `+0.05 × rank_position`.
- **Sparse:** a BM25-style normalised token-overlap scorer, `top_k = 4`.
- **Category steering:** ×1.5 multiplier if the chunk's category matches the loan type (with alias mapping — `housing→home`, `foir→underwriting`, `student→education`), ×0.85 if it doesn't.
- **Intent boosts:** +0.15 eligibility questions · +0.20 discrepancy/"why" questions · +0.20 FOIR/EMI/income · +0.25 KYC/PAN/Aadhaar.
- **Graceful degradation:** if ChromaDB is unavailable, the BM25 ranker carries retrieval alone. No hard dependency.

**Deterministic financial engine inside the assistant** — the assistant does *not* let the LLM do arithmetic:
- **EMI** by the standard amortisation formula: `P·r·(1+r)ⁿ / ((1+r)ⁿ−1)`
- **FOIR** with tiered policy limits: **50%** for income < ₹50,000 · **55%** for ₹50,000–₹1,00,000 · **65%** above ₹1,00,000
- **Maximum eligible loan amount**, back-solved from the maximum affordable EMI and rounded to the nearest thousand
- Returns `isFoirCompliant`, `proposedEmi`, `calculatedFoirPct`, `maxEligibleAmount`

**Output:** a grounded answer with **explicit citations** (`policyName`, `section`, `citationUrl`), plus a confidence signal. **Model fallback chain:** the configured Groq model, then `openai/gpt-oss-120b` → `openai/gpt-oss-20b` → `allam-2-7b` → `groq/compound-mini` → `groq/compound`. Any HTTP error rolls to the next model. The assistant stays up even when a provider degrades.

## 2.10 The applicant notification system (our newest subsystem — solves P3)

**Design constraint we set ourselves:** add no new source of truth. The feed is **derived entirely from existing audit records** — `Activity` status changes, officer document rejections, and `ValidationResult.checks`. No new collection, no duplicated state, nothing fabricated.

**Three notification kinds:**
- `decision` — from `Activity` action `Status Changed`, with per-status copy for approved / rejected / documents_required / under_review / withdrawn
- `document` — from `Document Rejected`, carrying the officer's `reviewComment`
- `issue` — **one digest per open application**, collapsing all flagged checks into a single notification instead of nine

**Machine codes translated to plain language** — the applicant never sees an enum:
`IDENTITY_NAME_MATCH → "Name mismatch"` · `SLIP_VS_BANK_SALARY → "Salary variance"` · `DECLARED_VS_SLIP_INCOME → "Declared income variance"` · `AADHAAR_VERIFICATION → "Aadhaar not verified"` · `PAN_CONSISTENCY → "PAN number mismatch"` · `DOB_CONSISTENCY → "Date of birth mismatch"` · `EMPLOYER_CONSISTENCY → "Employer name mismatch"` · `SLIP_VS_FORM16_INCOME → "Form 16 income variance"` · `EXISTING_EMI_BURDEN → "Existing EMI burden"`

**Privacy filtering:** internal officer `Note` records, LLM `recommendedAction`, and officer identities are **deliberately excluded**. Applicants see facts about their own documents, sorted highest-severity first, capped at 5 reasons per notification and 30 notifications per feed.

**Two surfaces, one request:** a topbar bell with an unread badge and a dashboard "Updates" panel share a module-level cache (in-flight promise + 30s TTL + listener set), so mounting both fires **one** API call, not two.

## SLIDE 7 — The 9 Checks ⭐ · M5 · 5 min `P1 P2`

**On the slide — a compact table:**

| Check | Compares | Flag threshold |
|---|---|---|
| `IDENTITY_NAME_MATCH` | name across up to 6 sources | fuzzy < 0.70 |
| `DOB_CONSISTENCY` | PAN vs Aadhaar DOB | any mismatch |
| `PAN_CONSISTENCY` | PAN vs slip vs Form 16 | any divergence |
| `AADHAAR_VERIFICATION` | 12-digit validity | invalid → WARNING |
| `EMPLOYER_CONSISTENCY` | slip vs Form 16 employer | fuzzy < 0.50 |
| `DECLARED_VS_SLIP_INCOME` | declared vs slip net | variance > 35% |
| `SLIP_VS_BANK_SALARY` | slip vs bank salary credits | > 35% or none found |
| `SLIP_VS_FORM16_INCOME` | annualised slip vs Form 16 | variance > 40% |
| `EXISTING_EMI_BURDEN` | EMI debits vs income | DTI > 50% |

**Plus:** every check emits `PASSED / WARNING / FLAGGED` × `LOW / MEDIUM / HIGH` **+ evidence + both compared sources**

**Say — go deep on exactly two, with live numbers:**
- **Name match:** collect the name from every source, fuzzy-compare each to the declared name, keep the **lowest**. Our live case: **17% → FLAGGED / HIGH**.
- **Income variance:** `|declared − slip| / declared × 100`. Live cases: **153.8%, 426.5%, 5171.7% → FLAGGED / HIGH**.

Then the scoring formula (`base = 40 + pass_ratio × 60`, `penalty = flagged×8 + warnings×3`, capped at 72 under review and 55 at high severity) and the line that lands it: **every point of that score is traceable to a named check on a named document pair.**

# PART 6 — Honest limitations (own these before the panel finds them)

**Disclose on slide 11:**
1. **No labelled-dataset accuracy benchmark.** Validated case-by-case on real documents; a benchmark set is the next milestone.
2. **Verification score is heuristic**, tuned by judgement — not calibrated against actual loan outcomes. It ranks files for officer attention; it is not a probability of default.
3. **Policy corpus is 14 chunks**, all HDFC. The retrieval architecture is bank-agnostic; the corpus is not yet.
4. **OCR degrades on low-DPI scans.** Provenance is tracked, but a bad scan is still a bad scan.
5. **Notification read-state is client-side** (localStorage) — a deliberate trade-off, not a server-side read receipt.

**Know internally — do not volunteer, but answer honestly if asked directly:**
6. **`DOB_CONSISTENCY` has a fallback-value weakness.** In `deterministic_validator.py:190-191`, when PAN or Aadhaar DOB isn't extracted, the check substitutes a default date, so it can report PASSED on data that was never actually read. The name check has a similar pattern — it falls back to the registered name when PAN/Aadhaar names are missing. **Correct answer if asked:** *"You're right — that fallback makes those two checks optimistic when extraction fails. The fix is to emit an INCOMPLETE status instead of substituting a value, and it's a small change we've scoped."*

> **Worth fixing before you present** — it's roughly a 30-minute change and it removes the only genuinely weak spot in the verification engine. If you want it done, say so and it'll be handled.

**Never claim:** that the system detects fraud (it detects *inconsistency*) · that it decides loans (the officer does) · any accuracy percentage you haven't measured · that the RAG corpus covers multiple banks.
